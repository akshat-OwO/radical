title: "Notifications API"
description: "Local reminders, native push, topic state, badges, and tap navigation."

`internalPlugins.notifications` enables local notifications, badges, and network. `internalPlugins.pushNotifications` also enables Firebase messaging and topic storage. Dependencies are `@capacitor/local-notifications@8.3.1`, `@capawesome/capacitor-badge@8.0.4`, `@capacitor/network@8.0.1`, and, for push, `@capacitor-firebase/messaging@8.5.2`.

## Client operations

| Export | Input | Success value |
| --- | --- | --- |
| `checkNotificationPermission` | Effect value | `"granted"`, `"denied"`, or `"prompt"` |
| `requestNotificationPermission` | Effect value | Same permission union |
| `checkExactAlarmPermission` | Effect value | `"granted"`, `"denied"`, or `"not-required"` |
| `requestExactAlarmPermission` | Effect value | Same exact-alarm union |
| `scheduleNotification(notification)` | `LocalNotification` | `NotificationScheduleResult` |
| `cancelNotification(id)` | Notification ID | Void |
| `registerPush` | Effect value | FCM token string |
| `subscribeToTopic(topic)` | Topic string | Void |
| `unsubscribeFromTopic(topic)` | Topic string | Void |
| `getNotificationTopics` | Effect value | Confirmed topic list on this installation |
| `isSubscribedToTopic(topic)` | Topic string | Boolean |
| `setNotificationBadge(count)` | Nonnegative integer | Void |
| `clearNotificationBadge` | Effect value | Void, equivalent to count zero |

Permission, scheduling, cancellation, and push registration depend on `Bridge | BrowserNotifications`. Topic and badge operations depend on `Bridge`. `notificationsLive(effect)` provides `BrowserNotificationsLive`. `browserNotificationsLayer` and `BrowserNotifications` support injected browser behavior.

## Input schemas

`LocalNotificationSchema` has required `id`, `title`, and `delaySeconds`, plus optional `body` and `route`.

| Field | Constraint |
| --- | --- |
| `id` | Integer from 1 through 2147483647 |
| `title` | Nonempty string |
| `body` | Optional string |
| `delaySeconds` | Finite number greater than zero |
| `route` | Optional app-relative path starting with one `/`; no backslash, whitespace, or control characters |

`NotificationRouteSchema` validates the route. `TopicSchema` accepts 1 to 900 characters matching letters, digits, `_`, `.`, `~`, `%`, or `-`. The `/topics/` prefix is not part of this input. `NotificationPermissionSchema` validates the permission union.

Native scheduling requests permission when it is prompt. A denied permission fails with `PermissionDenied`. Browsers schedule only while the page remains open. Native push and topics are unavailable in browsers. Topic lookup reports local confirmed state, not an FCM server query. Badges depend on native platform and launcher support.

## Exact alarms and schedule results

`notifications.android.exactAlarms` is an optional boolean that defaults to false. With local notifications enabled, true adds `android.permission.SCHEDULE_EXACT_ALARM` to the generated Android manifest. Push notifications also enable local notifications. False or omission preserves existing native output. This option has no effect on iOS and does not enable notifications by itself.

`checkExactAlarmPermission` and `requestExactAlarmPermission` require `Bridge`. On Android, they wrap Capacitor's `checkExactNotificationSetting` and `changeExactNotificationSetting`. The request opens Android's **Alarms & reminders** settings on Android 12 and later and returns the setting when the user returns. Denial is a success value, `"denied"`. Older Android versions report `"granted"` because they need no special access. Declaration alone does not grant access.

On iOS and browsers, both operations report `"not-required"` without a native call. iOS has no exact-alarm permission. This value does not imply notification display permission or guaranteed delivery timing. `ExactAlarmPermissionSchema` validates this union.

`NotificationScheduleResultSchema` decodes `notifications`, an array of `{ id: number }`, and optional `warning`, an object with string `code` and `message`. The corresponding types are `NotificationScheduleResult` and `NotificationScheduleWarning`. Warning code `"OS-PLUG-LNOT-0017"` means Android accepted the reminder as an inexact alarm because exact-alarm access was missing. Unknown warning codes are preserved. A missing warning is not a delivery-time guarantee. Browser scheduling returns the accepted ID without a warning.

Scheduling uses Capacitor's default exact-alarm behavior. On Android 12 and later, Capacitor can open settings when access is missing, then fall back to an inexact alarm if access remains denied. Requesting access before scheduling avoids consuming the delay in settings. Existing inexact alarms are not upgraded by a later grant. Android cancels future exact alarms when access is revoked. See [Android alarm behavior](https://developer.android.com/develop/background-work/services/alarms#exact).

Radical never adds `USE_EXACT_ALARM`. [Google Play restricts that permission](https://support.google.com/googleplay/android-developer/answer/13161072) to qualifying core alarm and calendar use cases.

## Navigation watcher

`watchNotificationNavigation({ appId, push?, onError? })` is a scoped, long-lived Effect requiring `Bridge`, `RadicalAdapter`, and `NotificationSnapshots`. It listens for tap actions, validates the route, and tries an exact stored snapshot when offline. Otherwise it uses adapter navigation. `push` defaults to false.

`NotificationSnapshotsLive` provides the browser cache implementation and browser network service but still requires `Bridge`. The service's `restore(route, appId)` returns whether a snapshot restoration started. Browser tap events use `radical-notification`.

## Errors and React hooks

`NotificationError` includes `PermissionDenied`, `Unavailable`, `MissingPushConfiguration`, and bridge errors. Invalid IDs, routes, topic names, counts, and out-of-range scheduled dates produce `Unavailable`. `MissingPushConfiguration` carries `reason` when the native shell lacks Firebase setup. Exact-alarm operations use the same typed bridge errors. Unknown native failures remain `BridgeCallFailed`; malformed results remain `BridgeDecodeError`.

`useNotificationPermission()` exposes `check()` and `request()`. `useExactAlarmPermission()` checks on mount and exposes `check()` and `request()`, with the exact-alarm union in `value`. `useNotifications()` exposes schedule, cancel, badge, push, and topic actions. Schedule actions retain `NotificationScheduleResult` in `value`, including warnings. Topic actions return the updated confirmed list in `value`.
