# Safe area

`safeAreaStyle(context)` is exported by `radical/server` and `radical/client`. It returns four CSS custom properties, `--radical-safe-area-top`, `--radical-safe-area-right`, `--radical-safe-area-bottom`, and `--radical-safe-area-left`. Apply the result to the document root during SSR, then reuse the same serialized native context during hydration.

Shell values are CSS pixels. Browser values are `env(safe-area-inset-*, 0px)`, so CSS follows the browser's safe area without waiting for JavaScript. Include `viewport-fit=cover` in the viewport metadata. Apply the properties where your content needs padding. Backgrounds can extend to the window edges.

`RadicalProvider` accepts `nativeContext` alongside its existing bridge layer. `useSafeArea()` returns `{ top, right, bottom, left }` from that context during SSR and hydration. After mount, it subscribes to bridge updates and releases the listener on unmount. In a browser, it measures an invisible `env()` probe and remeasures when the probe or viewport resizes. Without a native context, SSR returns zeros. CSS updates do not require React or a mounted hook.

For other UI libraries, `watchSafeArea(receive)` from `radical/client` is a scoped Effect requiring `Bridge`. It calls `receive` with current insets and never changes styles. Keep its scope alive until unmount. The TanStack example wires the request context through a root loader. Neither core function imports TanStack or React.

## First request and updates

Android waits for window insets before enabling network loads. It reads the union of system bars and display cutout, divides physical pixels by display density, and replaces the template seed's safe area before setting the native cookie. The WebView occupies the full window with no system-bar padding.

iOS waits until its view belongs to a window and has completed layout. It reads `view.safeAreaInsets` in points, writes every native cookie through `WKHTTPCookieStore`, and starts Capacitor's navigation after all writes finish. If the insets change during those writes, it repeats with the latest layout. Both shells trade a short startup wait for a first server response with correct insets. They never display a provisional page with zero padding.

On changes, both shells refresh the HttpOnly cookie before publishing a `radicalSafeArea` event through the bridge. A document-start script retains the latest value so a subscription mounted after the event still receives it. The script stores values by event name in `window.__radical.latest`, and `Bridge.observe` replays any event's latest value. CSS updates run after the SSR document finishes parsing, and on live updates. Each property is written only if its value differs, so the matching SSR styles remain untouched during hydration. Later requests use the updated cookie. Already cached offline HTML can contain an older context; offline snapshot refresh is outside this feature.

## Capacitor inset ownership

Capacitor 8's Android `SystemBars.injectSafeAreaCSS` changes the root element's inline style after page commit. React then sees attributes absent from SSR and reports a hydration mismatch. Generated shells set `plugins.SystemBars.insetsHandling` to `disable`, which disables that injection and Capacitor's inset padding. Radical owns both cookie values and CSS updates. Its Android listener pads the window by the visible IME height, which resizes the WebView so focused controls can scroll above the keyboard. While the IME is visible, the bottom safe area is zero because the keyboard padding already excludes the navigation bar. Closing the keyboard removes that padding and restores the system-bar inset. Keyboard height never enters the cookie. The iOS SystemBars plugin does not inject safe-area styles. Radical keeps Capacitor's default `contentInsetAdjustmentBehavior = .never`. UIKit adds no native safe-area padding, so the page applies that padding once through CSS. The controller observes keyboard frame changes and hide notifications. It converts the keyboard frame from the window screen's coordinate space into the view, then sets the scroll view's bottom content and vertical indicator insets to the intersection height. Hiding the keyboard resets both to zero. The controller removes its observers on deinitialization.

The WebView remains the full-window root view. Explicit scroll insets let WebKit reveal the bottom field and Submit on the Duo inner display, so frame resizing is unnecessary. Keyboard geometry never enters `view.safeAreaInsets`, the hook, the cookie, or the CSS variables. See the [simulator verification](verification/safe-area.md) for screenshots and the cover landscape tooling limitation.
