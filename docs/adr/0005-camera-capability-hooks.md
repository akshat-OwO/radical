# 0005: Camera capability hooks

Camera is the first action-based capability hook. Keep it opt-in because enabling it changes platform permission declarations and requires an app-specific explanation to users. `internalPlugins.camera: true` requires nonblank `pluginOptions.Camera.usageDescription` and `photoLibraryUsageDescription`, validated by the manifest and escaped when written to Info.plist. Generation adds Android `CAMERA`, optional camera hardware, and iOS `NSCameraUsageDescription` plus `NSPhotoLibraryUsageDescription`. Disabled camera contributes none of these or its npm dependency.

Use manifest-declared Camera 8.2.6 commands through the Effect bridge. Pin that version in the catalog, optional peer, and manifest because the structured `OS-PLUG-CAMR-*` errors and `takePhoto`/`chooseFromGallery` contracts define our normalization boundary. Map permission denial, user cancellation, and missing camera to `PermissionDenied`, `Cancelled`, and `Unavailable`. Preserve unknown rejection codes and invalid responses as bridge errors. The virtual module exposes Capacitor's command results; the capability Effects and hooks normalize them to `Photo`.

`Photo` owns a data URL and MIME type, with dimensions decoded from the image after EXIF orientation when the runtime can decode it. Native resolution metadata is sensor-oriented, so a portrait Android capture reports landscape metadata; decoding keeps dimensions consistent with what `<img>` renders in every runtime. Data URLs cost an extra in-memory copy but have no revocation lifecycle and survive rerenders and hook unmount. Native file URIs are read through Capacitor's local file URL conversion. Browser file inputs accept images and request environment capture. `choose` uses the native single-image gallery picker or a browser input without capture, allowing a library path on simulators without camera hardware. Camera requests ask only for camera. The library action requests photo-library read access on iOS through the upstream plugin. It never saves to the gallery, so no photo-library additions usage string is generated.

Permission checks report granted, denied, or prompt. Native requests ask only for camera. Browser checks query the Permissions API, returning prompt when the browser does not implement camera queries. Browser requests use getUserMedia and immediately stop every track, including results that arrive after Effect interruption. A file picker can still work when camera permission is denied because file selection and camera access are distinct browser capabilities.

Hooks render idle on the server and do not execute actions until mounted. Permission checks start after commit; capture and requests need explicit actions. A small bridge action hook owns one in-flight fiber, suppresses overlapping actions on that hook, and interrupts it on unmount or provider replacement. Browser inputs and readers release resources on every exit. Capacitor cannot cancel an open native picker; interruption abandons its result and suppresses state updates. Apps should keep a single camera hook mounted while its picker is open. Activity restoration after Android kills the process is outside this hook's contract.

## Build plan contributions

The build plan decodes Camera options once with the manifest schema. `camera-build.ts`, beside `camera-plugin.ts`, declares Android camera permission and optional hardware, plus the two iOS usage keys. Platform generators apply the resolved declarations without importing Camera code.

Camera and Video stream contribute to the same `NSCameraUsageDescription`. The explicit `unique-purpose` composition rule orders the still-camera purpose before the video purpose, removes identical text, joins distinct purposes with a space, and escapes XML after composition. Android declarations deduplicate by exact value. Conflicting values for other plist keys fail with `InvalidConfig` naming the key.
