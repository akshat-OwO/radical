# 0015: Location capability

Location is opt-in through `internalPlugins.location: true`, because enabling it changes permission declarations and needs app-specific explanations to users. Version 1 is foreground only. Background tracking, geofencing, geocoding, heading, and mock-location detection are separate future capabilities, because each brings its own store policy and platform declarations.

Do not rely on the stock WebView `navigator.geolocation` in shells. Without declarations it fails on both platforms. With them, iOS 17–26 shows the app's CoreLocation prompt and then a WebKit prompt naming the page's host, and the public delegate that would suppress the second prompt exists only from iOS 27. Neither WebView can report location precision, tell location services off from denial, or keep a grant reliably. Leaving `navigator.geolocation` denied in shells was rejected because map libraries call it directly.

Use `@capacitor/geolocation@8.2.4`, pinned like Camera in ADR 0005, for fixes, watches, permission, and the Android dialog to turn location services on. Its structured errors define the normalization boundary: `OS-PLUG-GLOC-0007` becomes `LocationServicesOff`, denial and iOS restriction become `PermissionDenied`, and timeouts become `LocationTimeout`. The plugin cannot report or upgrade iOS reduced accuracy, so a small radical Swift plugin reads `accuracyAuthorization` and requests temporary full accuracy using a purpose key from `pluginOptions.Location.precisePurposes`. The Android Play Services dependency is accepted; the plugin falls back to `LocationManager` without it. The upstream plugin requires `NSLocationAlwaysAndWhenInUseUsageDescription` even for foreground use, so both iOS usage strings are generated from the configured purpose.

Requests default to approximate, and `request({ precise })` asks for precise location through the classic runtime dialog. Google Play requires apps targeting Android 17 (API 37) to request the minimum precision a feature needs, to use the system `LocationButton` for one-off precise access, and to declare every use of `ACCESS_FINE_LOCATION` in the Play Console. The classic dialog stays allowed for ongoing features such as navigation and follow-me. The `LocationButton` flow needs a native view over the WebView and is a separate future capability. Permission is `{ state, precision }`, where precision is `precise`, `approximate`, or `unknown`; location services off is an error, not a permission state, because the device-wide switch and the app's permission are independent. `openAppSettings` lives with device info and `openLocationServicesSettings` with location.

When location is enabled, radical's client entry replaces `navigator.geolocation` and patches `navigator.permissions.query({ name: "geolocation" })` with versions backed by the native plugin, unless `replaceNavigator: false`. The first call from a third-party library prompts with default precision, as the browser would. Errors map to the standard `GeolocationPositionError` codes. The permissions patch is required because MapLibre's locate control caches a `denied` query result for the session.

Hook and replacement watches share one pool keyed by options, with reference counting, so a map's locate control and an app's `useLocationWatch` run one native watch. Watches pause natively when the app goes to the background and resume when it returns, without ending the subscription. The bridge's `listen` only covers `addListener` events, so it gains a typed callback subscription for `watchPosition` and `clearWatch`, with release on interruption.

On plain web the capability falls back to the browser API: precision is `unknown`, location services off surfaces as `Unavailable`, purpose keys are ignored, and both settings calls fail with `Unavailable`.
