# App-storage foundation

Enable `internalPlugins.appStorage` to include the shared native resolver. This slice supplies identity and backup roots for subsequent storage capabilities. It does not supply key-value, Keychain, SQL, or file operations.

The Effect API exports `resolveAppStorage`, `StoreIdentity`, `StoreRequest`, `StorageCapability`, `StorageName`, and `BackupClass`. The resolver requires the `Bridge` service. A request contains `capability`, `store`, `namespace`, `backup`, and `path`. The result contains `relativePath`, never a native container path.

Store and namespace names contain 1–128 lowercase ASCII letters, digits, underscores, or hyphens, starting with a letter or digit. Logical paths use forward slashes. The empty path identifies the store root. Absolute paths, empty components, dot components, backslashes, colons, and control characters are rejected. Native resolution rejects symlinks in the resolved path, including dangling links. iOS uses descriptor-relative access with no-follow flags. Android uses API 24-compatible lstat and no-follow opens.

Identity contains the capability, store, and namespace. It contains no origin or build identifier. Eligible policy metadata is backed up with eligible data. Excluded and cache policy metadata belongs to excluded storage. Resolution checks all existing store roots and policy records before creating a store. A restored data directory therefore retains its class even if its policy metadata is missing. Reopening an identity with a different policy returns `StorePolicyConflict`.

Android uses internal files for eligible data and policy records, `noBackupFilesDir` for excluded data and excluded/cache policy records, and the app cache directory for cache data. Generated legacy rules are empty, and data-extraction rules contain empty cloud-backup and device-transfer sections. No include entries are emitted: any include replaces Android's default traversal with an allowlist. Empty rules preserve credential-protected and device-protected data, including device_root, device_file, device_database, and device_sharedpref, as well as domains Android adds later. Excluded and cache roots are omitted by the platform itself; no redundant exclude entries are needed. Conflicting application-attribute contributions or existing template attributes fail with typed InvalidConfig; identical values deduplicate. Both old and new backup-rule attributes belong to the application element.

iOS uses Application Support for eligible and excluded data, and Caches for cache data. Excluded directories receive `isExcludedFromBackup`. RadicalStorageBackup uses Foundation URLResourceValues.isExcludedFromBackup and setResourceValues after saves. The shared replace helper reapplies exclusion after atomic rename; policy publication applies it to staged and published records. [Apple backup guidance](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup) requires reapplying the property after saves.

The build contribution API accepts `privacyAccessedApis`, a map from Apple API categories to reason codes. Generation unions reasons and bundles one privacy manifest. The resolver declares file metadata access under `NSPrivacyAccessedAPICategoryFileTimestamp`, reason `C617.1`, for metadata within the app container.

Browser and SSR operations fail with `Unavailable`. An installed shell missing the command returns `BridgeUnavailable`. Storage-specific errors contain no input values or native exception descriptions.

Web-data clearing preserves the app-storage cache root. Per ADR 0012, it removes installation-local notification topic membership even when notifications are disabled; that topic record is not app storage. Sign-out does not delete app storage. Namespaces separate data but do not authorize bridge callers. Platform backup controls do not guarantee exclusion from every device transfer.

Policy publication flushes a temporary record before publishing it atomically. Android publishes a nonempty policy directory by rename, which cannot replace another nonempty policy directory. iOS publishes with an exclusive hard link. An advisory lock serializes store creation and publication across callers. Abandoned temporary records do not become authoritative policy records.

## Confinement and native mutation ownership

Namespaces separate data, not authorization: any bridged JavaScript may request another namespace. Native app code sharing the app uid is trusted code, not a separate sandbox principal.

Android API 24 exposes no public descriptor-relative openat or mkdirat API. Per-component lstat and final-component O_NOFOLLOW checks alone cannot stop an independent native writer swapping a parent between validation and use. Radical therefore owns its private roots structurally: every Radical app-storage mutation in the shell process must run synchronously through RadicalStorageOwner.mutate, from validation through final use. This one owner covers all three roots and all capabilities, including future background jobs, directory creation, rename, replacement, and deletion. Internal filesystem helpers require the owner. No Radical API creates symlinks or returns writable native paths. Unrelated native code or another app process must not mutate these roots behind the owner; supporting another process requires routing its operations through the same shell owner. The advisory policy lock additionally coordinates policy publication.

iOS uses the same structural ownership invariant. All Radical app-storage mutations run synchronously through RadicalStorageOwner.withMutation or on its enqueue queue, including creation, save, staging, replacement, policy publication, and backup-property updates. Internal filesystem and backup helpers require that owner. No Radical API creates symlinks; arbitrary native code or another process writing behind the owner is outside the contract, just as on Android.

File access uses verified descriptors, but Foundation's supported backup property requires a URL. RadicalStorageBackup therefore checks lstat(path) against fstat(descriptor) before and after setResourceValues: the path must not be a symlink, and device and inode must match. A mismatch becomes a typed InvalidStorageInput rejection. The shared owner prevents another Radical task swapping a parent within that interval. Foundation failures become StorageIOFailed; no native paths or exception details enter error payloads. Raw extended-attribute formats are not part of the implementation.

Native key-value storage caches one writable SQLite connection per identity under the owner and never closes it, because closing the last writer of a WAL database checkpoints into the database and WAL. A cheap read-only preflight runs before the first writable open. After Radical detects corruption, through that preflight or a failing statement, it never checkpoints, truncates, deletes, or reinitializes the database or WAL, and the identity stays quarantined until the process exits. Its handle stays referenced and runs no further statements, and later calls fail before path resolution. A database that passes the preflight is treated as healthy: Android's open-time WAL truncate and automatic checkpoints may run, and they move committed data without losing any. Any future store deletion must join the owner and clear the cached entry before it removes files. See [key-value corrupt databases](key-value.md#corrupt-databases).

Deterministic native regression tests compile the production helpers directly. StorageOwnerTest schedules a competing parent-swap model after validation and waits until that thread is blocked on the owner; only the validated root receives the modeled namespace creation. StorageBackupTest uses the supported Foundation resource-value readback for roots, new files, staging, and replacement. It verifies an already swapped parent or inode is rejected before mutation and that a competing owned swap cannot run between validation and the Foundation call. The native test commands and device checks are recorded in the verification document.
